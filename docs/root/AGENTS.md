# Agent Guidelines and Codebase Knowledge

## Project Overview
os configures and hardens an existing Omarchy installation through native Bash provisioning. It manages system-level hardening, security daemon configurations, package debloating, and per-theme desktop folder color integration using pure native Bash automation and standard Unix system utilities.

Omarchy owns the desktop runtime and system identity. This repository configures its native commands, user paths and hooks through `make setup`; it does not build a distribution, install a replacement runtime or migrate an existing desktop.

`modules/conf/themes/data/excluded.list` owns excluded theme slugs. `theme-policy.sh` archives excluded stock themes and user overlays outside the native catalog; setup and installed update hooks reconcile the same policy. Root update hooks pin their command search path and all theme filesystem paths. Preview regeneration validates full monitor geometry and owned sample windows, restores notification state, and verifies live Zed palette changes on one running instance. Zed palette synchronization uses native `theme_overrides` in settings instead of custom theme files loaded only at startup.

`RUN_MIGRATIONS=1` runs native Omarchy migrations through `06-omarchy-migrations.sh` before OS debloating and hardening. Preserve retired Neovim settings under the user's Omarchy retired configuration directory through `retired-config.sh`; a remaining active Neovim config makes native migrations expect omarchy-nvim even before package provisioning. Never fabricate migration completion markers or modify packaged migration scripts.

`04-omarchy-restore.sh` is explicitly enabled by `RESTORE_OMARCHY=1`; it backs up user configurations before restoring native Omarchy defaults. `RESET_SNAPSHOTS=1` runs `scripts/lib/snapshot-baseline.sh` only after successful full setup. Create and verify the baseline before deleting earlier snapshots; never delete snapshot zero, active or default snapshots. Keep this operation within the privileged setup pipeline.

`01-os-namespace.sh` identifies previous provisioning namespaces through their installed root-owned i18n library or their canonical audit service. It archives their managed hooks and retires only their audit timers and keyboard backlight units before installing the OS equivalents, preventing duplicate schedulers and device services.

`scripts/lib/root-recovery.sh` refuses provisioning on temporary or snapshot roots. `make setup SCOPE=recovery` saves configuration backups on persistent home storage and rolls back the currently booted Snapper snapshot. Do not reset snapshot history before returning to a persistent root and verifying the restored desktop.

## Repository Architecture
The repository codebase is organized into distinct functional paths. The provisioning pipeline `scripts/setup.sh` runs as root to apply all system hardening, pacman debloating, and security configurations, delegating to discrete scripts under `scripts/lib/modules/`. The verification runner `scripts/verify.sh` performs automated assertion checks on kernel sysctl parameters, PAM configurations, firewall rules, and active security services. The modular test suite located in `tests/` executes exhaustive assertion suites spanning syntax integrity, desktop services, lockscreen regression prevention, kernel sysctl parameters, authentication controls, firewall rules, package debloating, security tooling, hardware power policies, modular pipeline architecture, and idempotency safety via `tests/run-all.sh`. Continuous Integration is configured under `.github/workflows/ci.yml` executing shell linting and multi-job matrix test suites. The legacy compatibility suite is in `scripts/test-os-compat.sh`. Logging is managed by `scripts/run-setup.sh` and interactive execution is supported by `scripts/launch.sh`. Desktop theming integration is implemented in `hooks/theme-set.d/folder-color` (folder colors), `hooks/theme-set.d/shell-icons` (icon family), `hooks/theme-set.d/cli-theme` (CLI colors). Persistence hooks live in `hooks/pre-refresh-pacman.d/99-os-persist` and `hooks/post-update.d/99-os-persist`, and the post-update hook runs as root. Editor and tool configuration modules are located in `modules/conf/<app>/`, and theme preview assets are located in `modules/theme-previews/`. The root `Makefile` provides standard targets for setup, keyring selection, verification, testing, hook installation, theme sync, and editor configuration installation. Operational runbooks are stored in `docs/skills/` and exposed through `.skills/` links. Internationalization is provided by the pure Bash dictionary engine `scripts/lib/i18n.sh`, the offline timezone-to-locale resolver `scripts/lib/locale-map.sh`, the localized `make help` renderer `scripts/lib/help.sh`, the hook bootstrap shim `scripts/lib/i18n-boot.sh`, and the translation catalogs under `scripts/lib/messages/`. The uniform preview normalization and the overlay store are owned by `modules/theme-previews/scripts/lib/theme-preview.sh`, consumed by both `scripts/lib/modules/30-theming.sh` and the post-update hook. The shared user-scope installer patterns are owned by `scripts/lib/userconf.sh`, which every `modules/conf/*/install.sh` must use instead of reimplementing backups or shell block replacement.

## Module Ownership and Boundaries
Stage modules under `scripts/lib/modules/` are loaded by `scripts/setup.sh` in a fixed order and are individually idempotent. Because every module is sourced rather than executed, a module must never call `exit`; it must use `return` to skip its own work. `00-env.sh` owns the environment and defines `user_as`, `aur_verified_install` and `omarchy_as`; every module that needs to act inside a real user session must call `user_as` for arbitrary commands and `omarchy_as` instead of invoking `os` directly, so the user runtime directory and D-Bus bus are forwarded. `10-debloat.sh` owns package removal and the pin list, `20-defaults.sh` owns the browser, editor, media player and file manager defaults including the single canonical `inode/directory` entry, using Nautilus for graphical file management and GTK file dialogs without full KDE or GNOME desktop stacks, `25-desktop-cleanup.sh` owns orphan launcher entry hygiene across system, OS and per-user application directories plus the pacman removal hook, `27-bootloader.sh` owns the verified GRUB candidate, the cyan text menu and its shared regeneration hook, `30-theming.sh` owns per-home hook installation and `62-keyring.sh` owns the GNOME Keyring Secret Service backend with Seahorse, and `32-omaqt.sh` and `35-shell-plugins.sh` own the optional desktop stack and shell plugin layer. `85-security-stack.sh` owns security packages and service policies; `94-security-audit.sh` owns scheduled malware, package advisory and system audits; `95-maintenance.sh` owns routine cleanup and log policies. Neovim and omarchy-nvim are retained for the terminal editor; Micro is retired while preserving personal configuration. `32-omaqt.sh` is opt-in and no-ops with a log line unless `OMAQT_URL` is exported, so no upstream URL is hardcoded anywhere in the repository. Hardening, power, cleanup, AI removal and gaze protection stages must never be reached from the debloat stages.

## Internationalization and Locale

Supported languages are `it`, `en`, `fr`, `de`, `es`, and `pt`. Scripts never hardcode user-facing English: every human-readable message is referenced by a symbolic key resolved through `t`, `log`, `warn`, and `err` from `scripts/lib/i18n.sh`, with English always loaded first as the fallback catalog. Catalogs are plain `key=value` files and must declare exactly the same key set and the same `%s` placeholder count across all six languages. The active language is resolved from `OS_LANG`, then `LANGUAGE`, `LC_ALL`, `LC_MESSAGES`, `LANG`, and finally `/etc/locale.conf`; any unsupported value falls back to `en`. `i18n.sh` and `locale-map.sh` are sourced libraries and must never alter the calling shell's options. `scripts/lib/i18n-boot.sh` is the self-contained bootstrap used by hooks and installers, which degrades to a minimal English stub when no catalog runtime is reachable. The module `scripts/lib/modules/05-locale.sh` derives the target locale, console keymap, and XKB layout from the system timezone through `resolve_target_locale`, `resolve_target_keymap`, and `resolve_target_xkb`, then persists them in `/etc/locale.conf`, `/etc/vconsole.conf`, `/etc/profile.d/os-locale.sh`, and the managed Hyprland `kb_layout` block, never hardcoding an `en_US` default. The `make lang` target lists the supported languages and marks the active one.

## Operational Commands
Workflow targets are exposed through the root Makefile. The `make setup` command invokes `pkexec bash scripts/setup.sh` to execute full system hardening. The `make verify` command invokes `bash scripts/verify.sh` to validate applied security assertions. The `make test` command invokes `bash tests/run-all.sh` to run the comprehensive modular test suite. The `make hook` command copies `hooks/theme-set.d/*` into `~/.config/omarchy/hooks/theme-set.d/` with executable permissions. The `make icons` command triggers immediate color synchronization for the active theme. The `make theme` command synchronizes both folder icons and Zed editor themes. The `make zed`, `make cli` commands (or `make editors` for all of them) install the corresponding configuration module. The `make clean` command removes previous setup logs. The `make lang` command lists the supported languages and marks the active one, while `make i18n-status` reports the resolved language, catalog path, and message count.

## Change Application Policy
Every system or session state change must be staged in the repository configuration first and applied exclusively through the privileged pipeline (`make setup`, which runs `pkexec bash scripts/setup.sh`). Agents must never hot-apply fixes directly to the live system: no manual `systemctl` start, stop, restart, mask or unmask, no manual copies into `~/.config`, `/etc` or `/run`, and no direct service manipulation outside the pipeline. Read-only diagnosis (`systemctl status`, `journalctl`, `busctl`, config inspection) is always allowed. Running the pipeline is the only actuation path, and it reconciles live state from the repository idempotently. `make setup SCOPE=keyboard`, `make setup SCOPE=bootloader` and `make setup SCOPE=security` use the same privileged entry point to apply only their owned policies.

## Kernel Hardening Configuration
Kernel sysctl parameters are persisted in `/etc/sysctl.d/99-security.conf`. Memory protections include `kernel.randomize_va_space = 2`, `kernel.kptr_restrict = 2`, `kernel.dmesg_restrict = 1`, `kernel.perf_event_paranoid = 3`, `kernel.unprivileged_bpf_disabled = 1`, `kernel.yama.ptrace_scope = 1`, and `kernel.sysrq = 16`. Filesystem security includes `fs.suid_dumpable = 0`, `fs.protected_hardlinks = 1`, `fs.protected_symlinks = 1`, `fs.protected_fifos = 2`, and `fs.protected_regular = 2`. Network stack hardening includes `net.ipv4.conf.all.rp_filter = 1`, `net.ipv4.conf.all.accept_redirects = 0`, `net.ipv4.conf.all.send_redirects = 0`, `net.ipv4.conf.all.accept_source_route = 0`, `net.ipv4.icmp_echo_ignore_broadcasts = 1`, `net.ipv4.tcp_syncookies = 1`, and `net.ipv4.tcp_rfc1337 = 1`.

## Authentication and PAM Policies
Authentication security is enforced through `/etc/security/faillock.conf` which locks accounts for 900 seconds following 5 consecutive failed attempts. Password complexity rules are enforced in `/etc/security/pwquality.conf`. Access lists are controlled in `/etc/security/access.conf` and core dumps are disabled globally via `/etc/security/limits.d/99-no-core.conf`.

## Firewall and Service Isolation
The UFW firewall operates with default deny incoming and default allow outgoing policies, enabled at boot via `ufw.service`. SSH is hardened in `/etc/ssh/sshd_config.d/hardened.conf` disabling root login and password authentication while enforcing modern ciphers. Sandboxing drop-in `/etc/systemd/system/sshd.service.d/hardened.conf` applies `ProtectSystem=strict`, `ProtectHome=yes`, and `NoNewPrivileges=yes`. Unneeded daemons such as `avahi-daemon.service` and `cups.service` are disabled. Security services including `ufw.service`, `auditd.service`, `fail2ban.service`, and `usbguard.service` are enabled. NetworkManager is preserved without creating conflicting configuration overrides.

## Security Tooling Stack
Host security tools include `lynis` for system audits, `rkhunter` for rootkit scanning, `clamav` for virus scanning, `arch-audit` for Arch advisories, `auditd` for audit logging, `usbguard` for USB authorization, `fail2ban` for intrusion deterrence, and `apparmor` with mandatory access control profiles for `sshd`, `useradd`, `curl`, and `wget`. The weekly scanner covers `/home`, `/root`, `/etc`, `/usr`, `/opt`, `/var` and `/boot`; reports are retained under `/var/log`. These checks improve detection but cannot establish that the machine has no malware, CVEs or information leaks.

## Hardware and Battery Power Management
Battery longevity is enforced via a perpetual 75% charging threshold policy configured in `/etc/os/power.conf`. Multi-layered persistence guarantees enforcement across boots, kernel updates, hotplugs, and suspend/resume cycles through udev rules in `/etc/udev/rules.d/98-battery-charge-threshold.rules`, systemd-tmpfiles drop-in `/etc/tmpfiles.d/battery-charge-threshold.conf`, and systemd service `battery-charge-threshold.service`. Universal sysfs targeting applies to all existing and future batteries (`BAT*`, `BATT*`). Enforcement is capability-probed, never assumed: `scripts/lib/set-battery-charge-limit.sh` is the single authority, it writes a threshold only through an interface whose read-back is a real integer, verifies the value actually stuck, and records the outcome in `/run/os/battery-charge-limit.state`. `scripts/verify.sh` derives its verdict from that state through `--query`, fails when a supported interface drifted from the policy, and skips explicitly when the machine firmware exposes no charge threshold interface at all, which must never be reported as an enforced limit.

Keyboard backlight policy is owned by `scripts/lib/modules/91-suspend-resume.sh` and `scripts/lib/keyboard-backlight.sh`. Unit templates live in `modules/conf/power/data/`. Device services must run after the corresponding native systemd brightness restore. Preserve the upstream pre-hibernation shutdown and apply the hardware maximum only while awake or after resume. Do not write display or lock-indicator LEDs.

## Regression Prevention and Safety
System hardening and package debloating must strictly avoid breaking desktop functionality and user workflow. Core services including D-Bus session bus, Polkit authorization (`polkit.service`), PipeWire/WirePlumber audio (`pipewire.service`), NetworkManager, and display managers (`gdm`, `sddm`, `greetd`, `lightdm`) must never be blocked or deprived of necessary permissions. Hardening must strictly prevent double lockscreen occurrences and frozen or fake blank screen overlays by enforcing a single canonical screen locker per session, proper PAM authentication integration, non-conflicting idle/sleep triggers, and unblocked HID input devices in USBGuard. All modifications must be verified against `scripts/test-os-compat.sh` and `scripts/verify.sh`.

## Single Source Rules
Every rule has exactly one home. Documentation content lives under `docs/`; required root, module, GitHub and `.skills/` entry points use symlinks. Do not duplicate scripts, modules, tests, runbooks or catalogs. The root `scripts/`, `hooks/`, `tests/` and `modules/` own code; `.skills/` exposes the normative runbooks in `docs/skills/`. App-specific configuration lives under `modules/conf/<app>/`; focused subprojects, plugins and theme previews live under `modules/`. Each project stores its own stage modules in `<project>/scripts/lib/modules/`; shared stages stay in the root `scripts/lib/modules/` and are sourced by consumers. `.agents/skills` is always a symlink to `.skills`.

## Commit Conventions
All commit messages must follow the Conventional Commits standard formatted strictly as `<type>: <description>` or `<type>(<scope>): <description>`. The colon `:` following the target type is the only allowed punctuation or symbol. Titles must never contain emojis, exclamation marks, or extra punctuation.

## Scripting Rules and Constraints
Function names use descriptive words without digits. Do not wrap existing entrypoints in cosmetic classes or namespaces.

Scripts must use strict execution modes `set -euo pipefail` in pure native Bash without Python dependencies. Never use `|| true` to suppress failures; use `|| warn "message"` for non-critical steps that can fail gracefully. Do not add comments to Makefile or hook scripts. Do not hardcode user paths; derive directories from `$HOME` or `/home/*`. All operations must run in the foreground without `systemd-run`. All modifications to `scripts/setup.sh` and `scripts/verify.sh` must remain strictly idempotent.

## Mandatory Skill Loading and Pull Requests

At the start of every task, read every `.skills/*/SKILL.md` into the agent context. This inventory must contain every local skill; update it in the same change whenever a skill is created, renamed or removed. Subproject agents inherit this rule from the root AGENTS.md.

Treat `main` as read-only. All changes, including maintenance and GitHub policy changes, originate on a feature branch and enter `main` through a pull request. Never push directly to `main`, force push it, or rewrite its published history. Published commits remain historical facts; corrections and reversions also require pull requests.

Published releases are immutable by default. Never replace, delete, or add assets to an existing release, move or reuse a published version tag, or rewrite its release metadata. Corrected artifacts and release notes require a new version, and release automation must fail when the target version already exists. Keep every published version available as a historical record.

The canonical GitHub ruleset is `.github/main-ruleset.json`: no bypass actors, no branch creation or deletion, no force pushes, signed commits, linear history, squash-only pull requests, no mandatory approvals, stale approval dismissal, no additional latest push approval, resolved review threads, and successful CI and SAST checks against the latest base. Do not enable the blanket update restriction: without bypass actors it also blocks legitimate PR merges. Apply repository settings with the GitHub API and verify the active ruleset after applying it.

## Arch independence transition

The requested target is Arch Linux without the Omarchy runtime, with equivalent desktop and system functionality. The current implementation still requires Omarchy. `modules/platform/arch/data/parity.json` owns the capability inventory and official repository policy; `scripts/lib/arch-migration.sh` provides a read-only assessment. Never interpret installed package names or green legacy tests as replacement parity. Preserve the existing runtime, repositories, keys, kernel fallback and recovery entries until independent replacements, trial session, cold boot, suspend and recovery are verified. Removing Omarchy is not yet implemented by setup.

HyprMod is the graphical Hyprland settings application. Its stable application source and pure library wheels are pinned by hash in `modules/conf/hyprmod/data/requirements.lock`; system GTK bindings stay managed by pacman. The Bash installer preserves its generated `hyprland-gui.lua`, validates the staged compositor configuration and adds its include after managed defaults. User initiated GUI changes are stored automatically by HyprMod; agents still apply provisioning through setup. `make setup SCOPE=settings` installs and reconciles this integration without provisioning a GNOME desktop. Wallpaper generation belongs to `modules/conf/desktop/scripts/wallpaper.sh` with palette and layout policy separate from code. Stock wallpapers leave the active chooser catalog and are archived outside it; packaged originals and personal backgrounds are preserved.

The independent `os app` route belongs to `modules/os/`; role policy is JSON under `data/` and launcher algorithms are under `scripts/lib/`. `make setup SCOPE=cli` reconciles its installed executable, shared library, policy and catalogs without changing desktop configuration. Other groups remain delegated. Implementing application dispatch alone must never mark a migration capability verified.

Desktop health reconciliation belongs to `scripts/lib/desktop-health.sh` through `make setup SCOPE=desktop-health`; interface-only reconciliation belongs to `scripts/lib/desktop-interface.sh` through `SCOPE=interface`. HyprMod visual policy is separate JSON, CSS and icon mapping data with an exact patch against the pinned source. Preserve user compositor settings and explicit auto-save preferences.

The user authorized a staged migration to Ruby and Lua. Ruby owns new pure boot menu parsing and validation under `modules/platform/arch/scripts/`; Lua remains the compositor configuration language. Existing Bash provisioning stays available until equivalent integration tests and recovery paths cover each replacement. Ruby uses standard libraries and native packaged dependencies. Do not rewrite the provisioning pipeline in a single unverified change.

`SCOPE=boot-assessment` records and validates existing EFI entries. `SCOPE=grub-trial` installs a candidate without changing firmware BootOrder or removing Limine. Boot menu policy is JSON and the parser is Ruby. Never mark a trial boot verified from installation or syntax checks; preserve encryption, resume and per-snapshot command lines.
