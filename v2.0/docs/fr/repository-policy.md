# Politique du dépôt

[Italiano](../it/repository-policy.md) · [English](../en/repository-policy.md) · [Français](repository-policy.md)

`v2.0/data/repository/main-ruleset.json`, exposé comme `.github/main-ruleset.json`, est la politique canonique de protection de main. Sa cible est `refs/heads/main` avec application active et aucun acteur exempté : la création, la suppression et les poussées forcées sont bloquées, les commits doivent être signés, l’historique est linéaire, les demandes de fusion s’unissent uniquement en squash, aucune approbation n’est obligatoire, les approbations périmées sont annulées, les discussions doivent être résolues et les contrôles requis sont évalués sur la dernière base. La restriction générale des mises à jour reste désactivée car, sans acteur exempté, elle bloque aussi les fusions légitimes.

L’algorithme qui vérifie et applique cette politique est `src/component/repository/policy.lua`, avec les noms de commandes dans `data/core/commands.json` et sa propre politique dans `data/repository/policy.json`. Le composant lit le fichier canonique, énumère toutes les pages des règles avec `gh api --paginate --slurp`, résout le nom canonique sur toutes les pages et rejette un doublon ambigu. L’application crée la règle manquante avec `POST` ou met à jour l’existante avec `PUT`, puis la relit et la compare.

La comparaison est structurelle. Elle vérifie chaque champ canonique, accepte les métadonnées supplémentaires et les tableaux imbriqués renvoyés par l’API, et distingue les tableaux des objets même lorsqu’ils sont vides. Les tableaux doivent conserver la même cardinalité avec les mêmes éléments indépendamment de l’ordre et en comptant les doublons : une règle supplémentaire, un acteur exempté ajouté ou une restriction de mise à jour sont rejetés avant que le hook local ne soit satisfait. La valeur `null` est comparée explicitement et un champ canonique manquant échoue.

L’entrée en lecture seule est `script/os-lua repository-policy-check <propriétaire>/<dépôt>` ; `repository-policy-apply` effectue la modification et ne doit s’exécuter qu’après un contrôle réussi. Le hook `.githooks/pre-push` est une entrée Lua qui lit les enregistrements de poussée sur l’entrée standard et refuse une référence `main` directe ou supprimée tout en autorisant les branches de travail et les enregistrements répétés ; les enregistrements malformés échouent. Git exécute le hook depuis la racine de l’arbre de travail, donc les chemins relatifs du runtime se résolvent.

Les commandes vérifiées requièrent GitHub CLI avec un jeton authentifié, et l’application de la protection est une opération privilégiée qui exige la portée d’administration du dépôt. Les tests automatisés exercent le composant avec des backends isolés et n’appellent jamais l’API réelle ; la protection active sur le serveur est inspectée séparément par le workflow de provenance.
